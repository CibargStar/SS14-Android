# Архитектура и границы совместимости

Требования пользователя от 28 октября 2026: все серверы официального хаба, произвольные серверы по адресу, полноценные обновления, сенсорное управление, APK через GitHub/сайт. Задача не ограничивается одним заранее скомпилированным Content.Client.

Уточнение пользователя: требуется полноценный порт без сокращения клиентских возможностей. Полнота — критерий приёмки конечного продукта, а промежуточные runtime/engine-стенды — способы проверки реализации.

**Сохранение функциональности**

- Сохранить игровые системы, окна и инструменты клиента, чат, инвентарь, действия, звук и музыку, необходимые серверному контенту модули, авторизацию, reconnect и обновления. Возможности администратора доступны при соответствующих правах на сервере.
- Платформенные интеграции переносить через Android-реализации с сохранением пользовательского назначения: например, выбор файлов и встроенный веб-контент требуют соответствующего backend. Неперенесённая функция учитывается как открытая задача, а не удаляется из требований.
- Сенсорные элементы вызывают исходные игровые команды. Изменение расположения и взаимодействия с окнами сохраняет доступ к их функциям. Поддержка внешней клавиатуры и мыши также входит в цель.
- Оптимизация должна сохранять семантику игры и видимость объектов. Настройки графики могут предоставлять выбор качества; принудительное постоянное отключение возможностей не заменяет их перенос.
- Статус функциональной совместимости подтверждается испытаниями на серверных сборках. Неизвестные ограничения явно фиксируются; цель поддержки серверов не сужается до заранее выбранного форка.

**Совместимость определяется возможностями сборки сервера, а не белым списком названий.** Нельзя заранее гарантировать подключение к произвольному будущему форку, который использует неподдерживаемый нативный модуль, изменённый протокол или собственный движок. Для стандартных серверов цель — исполнять их исходный управляемый клиентский контент без отдельного APK под каждый сервер. Исключения должны иметь техническую причину и понятную диагностику.

**Три независимо обновляемые части**

1. **Android host APK.** Runtime, SDL/JNI, нативные Android ARM64-библиотеки, launcher Activity, мобильный ввод, управление игровым процессом. Обновление: загрузка подписанного APK, системная установка поверх приложения с тем же application ID и signing key. Обновление APK без root требует действия пользователя; обычное приложение не может обещать тихую установку. Нативные изменения первоначально доставлять через APK, чтобы не зависеть от загрузки исполняемых файлов из writable app data.
2. **Версионированный Android engine.** Управляемые библиотеки Robust с минимальными платформенными изменениями, собранные из нужной upstream-ревизии. Для каждого пакета фиксируются upstream revision/version, Android patch revision, runtime/TFM, host ABI, необходимые native modules, hash и подпись. Платформенные изменения должны сохранять API и сетевое поведение соответствующей версии. Если новые требования выходят за host ABI — сначала обновляется APK.
3. **Серверный контент.** Content.Client, Content.Shared, зависимости и ресурсы конкретной сборки через обычные API /info, ACZ/client.zip. Номер версии и ресурсы не заменяют DLL. Сохранить штатную проверку сборок Robust и согласование с сервером; отключение sandbox или подмена номера версии не считаются совместимостью.

**Порядок подключения**

Хаб/прямой ss14[s] URL → server /info → точная build identity и engine requirements → подбор совместимого Android engine → проверка подписи и host ABI → загрузка/проверка контента → запуск engine в игровом процессе → обычная авторизация и handshake → игра.

Смена движка сначала проектируется через завершение отдельного Android-процесса игры и новый запуск с другими пакетами. Launcher и cache manager остаются отдельным процессом. AssemblyLoadContext помогает разделять управляемые сборки, но сам по себе не гарантирует очистку SDL, native state, статических событий и всех библиотек. Desktop Process.Start нельзя механически перенести; нужен Android service/process bootstrap с собственной схемой запуска. Механизм выбирается после runtime/SDL-прототипа.

**Пакеты и публикация обновлений**

- Android engine catalog — собственный дополнительный каталог; официальные desktop подписи нельзя использовать для изменённых Android-бинарников. Исходные серверные пакеты сохраняют их штатную проверку.
- Пакеты неизменяемы, адресуются по hash; скачивание идёт во временный файл. Подпись и целостность проверяются до использования; переключение активной версии атомарное. Предыдущая рабочая установка сохраняется до проверки новой, откат не должен обходить запрет известных небезопасных версий.
- Ключ подписи Android APK и ключ каталога движков — разные назначения. Закрытые ключи не входят в исходники и APK.
- Android pipeline отслеживает используемые upstream версии, собирает соответствующие managed engine пакеты и проверяет совместимость native ABI. Нет необходимости пересобирать серверные Content.Client для ARM64, если они обычный совместимый IL; native/desktop-only зависимости требуют отдельного решения.
- Runtime не может автоматически исполнять сборку, рассчитанную на более новую версию .NET. Каталог должен выражать это требование и при необходимости предлагать обновление host APK.

**Сенсорный ввод**

Ввод следует подключать к существующим игровым BoundKeyFunction, сохраняя семантику серверных команд. Эмуляция одного курсора недостаточна для одновременного движения и действия.

- независимые pointer IDs: движение, наведение/взаимодействие и кнопки одновременно;
- движение, прицеливание и основной/альтернативный use, руки, бросок, drop, pull, examine;
- правила различения tap, hold, drag и swipe; отмена захвата при смене фокуса, закрытии окна и уходе в фон;
- контекстное меню для объектов под пальцем, настройка размеров и расположения кнопок;
- drag/drop инвентаря, перенос и изменение размеров игровых окон;
- чат, переключение каналов, Android IME и раскладка при открытой клавиатуре;
- мышь/клавиатура и сенсорный ввод используют одни игровые команды.

Тестирование действий должно включать одновременно движение, удержание модификатора и выбор объекта. Изменять протокол игры ради мобильных кнопок по умолчанию не требуется.

**Этапы с проверяемым результатом**

1. Runtime gate: отдельно собранные DLL загружаются на реальном ARM64-устройстве; работают IL emit, expressions, generics/reflection и нужные сборки NetSerializer. Сравнить Mono JIT и доступный экспериментальный CoreCLR. Текущий стенд покрывает только первые несколько условий.
2. Engine gate: загрузить пакет Robust с Android-патчами, поднять SDL/GLES и звук, сохранить проверки контента. Запустить движок без вшитого Content.Client.
3. Content gate: скачать оригинальный контент и войти на несколько независимых актуальных форков с различающимися сборками. Испытать смену двух версий без утечки процесса/нативного состояния.
4. Update gate: Android engine/content update без переустановки APK; отказ от повреждённого/неподписанного пакета; восстановление после обрыва загрузки и аварийного завершения. Отдельно системное обновление APK с сохранением настроек.
5. Input gate: полный игровой цикл на телефоне без внешней клавиатуры, включая чат, инвентарь, контекстные действия и бой.
6. Release gate: Adreno/Mali, планшет/телефон, длительная сессия, фон/возврат, потеря сети, reconnect, нагрев, память, frame-time. Список подтверждённых серверных сборок публикуется как результаты испытаний, а не как искусственный whitelist.

Перед выпуском сопоставить возможности с соответствующей версией настольного клиента: для каждой функции должны быть реализация и результат проверки на Android. Незавершённые платформенные модули или недоступные с сенсорного экрана действия означают, что полный порт ещё не готов.

**Факты начального обследования**

Официальный engine manifest получен 28 октября 2026; содержит 1045 записей версий и RID freebsd-arm64, freebsd-x64, linux-arm64, linux-x64, osx-arm64, osx-x64, win-arm64, win-x64. Android RID отсутствует. Это каталог исторических версий, не число версий, используемых серверами сейчас.

Основной hub /api/servers и штатный fallback в этой среде вернули 403, поэтому инвентаризация действующих серверов не выполнена. Нельзя приписывать хабу результаты анализа engine manifest. Исходники штатного launcher дают реализацию API и URL-преобразований, которые следует переиспользовать или перенести с сохранением лицензии.

Ранее найденный неофициальный порт полезен как источник платформенных исправлений, но вшитые engine/content и его ограничение по версиям не удовлетворяют требованиям универсального клиента. Автоматическая применимость его патчей к текущему upstream не установлена.
